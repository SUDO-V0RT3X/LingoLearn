Media & Taxonomy after the merge

Your taxonomy tables became the single tag model for the project, your upload is now what the content builder actually uses, and the author dashboard shows real content. The routes moved behind the auth gate.

What was kept

Yours
  • 400_taxonomy.sql (renumbered from 410) is the tag schema. TD's tag_vocabulary was deleted from 300_content.sql; your tags and content_tags won, including tag_type, descriptions and the ten-tag trigger.
  • TaxonomyMethods and its SQL, unchanged.
  • validateAudio shared by frontend and backend, memory storage with validation before anything is written, and the duration check.
  • The author dashboard: ContentStatusBadge, ContentFilterPills, RejectedContentNotice, contentStatusMeta and the Feedback tab.
  • Your upload button and <audio> preview, ported into the builder's audio block and living inside that component, as they did in yours.

The tag collision, and how it was settled

Both you and TD created a table called content_tags, with different columns. Both use CREATE TABLE IF NOT EXISTS, so on a merged database whichever migration ran first won and the other was skipped with no error at all — your queries would have failed at runtime on missing ct.id and ct.created_at.

Now
VocabularyYour tags(id, name, tag_type, description). Themes are the union of both lists: your six plus greetings, numbers, shopping, directions, weather, conversation, vocabulary, listening, grammar.
Link tableYour content_tags shape, plus real foreign keys: content_id → content(id) ON DELETE CASCADE and tag_id → tags(id) ON DELETE RESTRICT. Deleting content removes its links; a tag in use cannot be deleted. It had no foreign key to anything before, and the tests used a made-up content_id of 42.
LevelsYour levels table stayed, seeded 1–6 instead of 1–5, because the API, the builder, Explore and the review queue all use six.
The builder's tag listFetched from getTags?type=theme. The hard-coded AVAILABLE_TAGS array is gone, so an administrator adding a tag changes what authors see.

How much new code is in your slice

Almost none

An image upload was written during the merge and then removed again: it was a second copy of your audio path, and image blocks already worked with a typed link. Uploading is audio only, as you left it. Adding images is still yours to do, and now has an obvious shape to follow.

What remains that you did not write is one file, functions/mediaStorage.ts: where an upload is written and how it is named. That was needed to fix the filename and the Host-header URL, both described below.

The dashboard is on real data

  • mockAuthorContent is deleted. The store calls ContentDataSource.getMyContent(), which returns only the signed-in author's own content.
  • Feedback comes from getMyFeedback: the real moderator note, who decided and when, for the Feedback tab.
  • Row ids are integers, and Edit opens /content-builder/:contentId — the builder used to ignore the ?id= you sent.
  • type is derived: a quiz shows as Test, anything else as Lesson. Levels and titles are real columns now.

What is yours to do next

  • Image upload. Image blocks still take a typed link. The audio route is the pattern: receiveFile → validate → storeUpload → return a relative fileUrl.
  • An asset table, if uploads should be tracked in the database (filename, type, size, duration) — the idea from your old media-MO branch worth salvaging. That is also what a safe delete needs.
  • The media library screen: it is currently a standalone Upload Audio page, while the builder uploads inline. Decide whether it becomes a picker.
  • Level names and descriptions are unused on the frontend so far.
